# 星律樣板總成樣板提醒與卡死告警設計

## 目標

為星律樣板總成補齊兩類可恢復告警：

1. EAEP 上傳樣板時，若樣板配方類型不屬於目標星律所連主機的配方類型，必須二次確認後才能上傳。
2. 樣板下單並收到原料後，若在可配置等待時間內沒有任何原料被主機取用，標記槽位並向相關玩家廣播診斷資訊。

兩類告警都在星律專用樣板槽上繪製醒目的紅色邊框。實作只修改 `gt_shanhai` 的山海署名檔案，不修改 EAEP、AE2、GTCEu 或 GTLCore 原始檔。

## 非目標

- 不改變星律的配方搜索、配方類型切換、樣板身份守衛或原料扣用規則。
- 不把樣板製作者視為 AE 下單者。
- 不建立獨立 HTML 或自訂大型 GUI。
- 不將一次告警改成週期洗屏；原料快照未變時只告警一次。
- 不部署 jar；部署由後續明確指令決定。

## 方案選擇

採用「AE CPU 下單者作用域 + 星律槽位服務端狀態機 + 既有 EAEP 選擇畫面攔截」方案。

AE2 的 `ExecutingCraftingJob.playerId` 是下單者的權威來源，且會隨合成工作持久化。`CraftingCpuLogic.executeCrafting()` 呼叫 provider 的 `pushPattern()` 時，以短生命週期 `ThreadLocal` 暴露本次工作的 player id；星律的 `pushPattern()` 成功定位槽位後立即取走該 id。作用域必須使用 `try/finally` 清理，不能跨越一次 provider 呼叫。

不採用樣板 NBT 的 `encodePlayer`，因為它表示樣板製作者而不是本次下單者。也不採用全服廣播，避免無關玩家收到大量機器告警。

## EAEP 錯誤主機確認

### 資料

沿用現有 `ProvidersListS2CPacket` 擴充鏈路，除每個 provider 的主機配方類型列表外，再附加每個 provider 的 `isStellar` 標記及本次待上傳樣板的精確配方類型 ID。`isStellar` 用來區分「不是星律」與「已知是星律但目前沒有主機配方類型」；服務端分別從 Ctrl+Q 待上傳樣板或編碼終端的已編碼樣板槽讀取樣板類型欄位。

配方類型判定規則：

- 樣板類型未知時不攔截，避免普通 AE2 樣板或舊樣板誤報。
- 目標不是星律或封包沒有星律標記資料時不攔截，保持舊封包相容。
- 已知目標是星律但主機配方類型為空時視為不相容。
- 主機包含樣板精確類型時相容。
- 主機類型與樣板類型位於 `recipeTypeSharedSearchSets` 同一組時相容。
- 其餘情況視為錯誤主機。

### 互動

在 `ProviderSelectScreen.onChoose(int, boolean)` 發送原封包前攔截。錯誤主機時開啟 Minecraft 原生 `ConfirmScreen`，顯示樣板配方類型、目標星律名稱與目標主機配方類型。確認後以一次性 bypass 標誌重新進入原方法並發送 EAEP 原封包；取消則返回原 provider 選擇畫面，保留待上傳樣板。

EAEP 的唯一匹配自動上傳也必須經過同一攔截，不能繞過二次確認。這是防誤操作功能而非安全邊界，服務端不拒絕手工偽造的 EAEP 封包。

## 槽位警告狀態

每個普通星律樣板槽維護兩個服務端判定結果：

- `WRONG_HOST`：槽位樣板有類型，但目前連接主機沒有精確或共享集合相容類型。
- `STUCK_INPUT`：槽位已有 AE 發配原料，且等待時間內所有原料數量都沒有下降。

普通槽位的警告集合序列化成緊湊字串並以 `@DescSynced` 同步。字符串只在集合實際變化時重建，客戶端按值變化解析，避免每幀分配。通配符母槽不在主樣板網格內，不繪製此紅框；其動態展開槽仍參與服務端卡死診斷，但通知中的槽位以母槽與展開索引標識。

`CachedPatternPaginationUIManager` 向 `CachedPatternSlotWidget` 傳入當前槽位警告查詢。槽位在原背景之上、物品圖示之外繪製固定 2 px 亮紅邊框，不改變槽位尺寸、分頁布局、輸出數量文字或 EAEP 高亮。

`WRONG_HOST` 在樣板變更、主機控制器變更、主機類型變更與區塊載入後重新計算。樣板被移除或重新連到相容主機時立即清除。

## 卡死狀態機

服務端以低頻訂閱檢查活躍槽位，不增加每 tick 全槽位解碼：

1. `pushPattern()` 成功後，保存槽位的下單者 player id、物品／流體原料快照與開始 tick。
2. 每秒檢查一次受監控槽位。槽位失活或原料清空時清除監控與 `STUCK_INPUT`。
3. 任一物品或流體數量下降，表示主機已實際取料；用剩餘原料建立新快照並重新計時。
4. 原料增加或種類變化表示收到新發配；更新快照並重新計時。
5. 快照完全不變且經過 `stellarPatternStuckTimeoutSeconds` 後，設置 `STUCK_INPUT` 並廣播一次。
6. 同一快照告警後不重複廣播；原料再次變化才形成新的監控週期。

預設等待 10 秒，配置範圍 1 至 3600 秒。設定位於現有 `recipe_type_pattern_buffer` COMMON 配置段，變更後按 Forge COMMON 配置的既有載入方式生效。

## 卡死原因與診斷資料

告警時收集以下資料：

- 星律名稱、維度、世界座標與槽位號。
- 樣板第一輸出及完整輸出摘要。
- 未被取用的物品與流體及其數量。
- 目前連接主機公開的配方類型 ID。
- 樣板配方類型 ID。
- 槽位是否存在已解析 GT 配方快取。
- 已解析配方的類型與主輸出是否和樣板身份一致。
- 關聯控制器 `recipeLogic` 的 `IRecipeStatus.getRecipeStatus()` 與 `getWorkingStatus()` 非成功原因，按文本去重。

原因優先級為：錯誤主機類型、未找到／未快取配方、GTLCore/GTCEu 原生錯誤、配方身份不一致、原料長時間未取用。原生錯誤可能包含未找到配方、輸入不足、輸出阻塞、能源不足、電壓、維護或自訂配方條件；本功能只讀取並展示，不改寫主機狀態。

## 廣播與去重

收件人集合是以下兩組玩家的 UUID 聯集：

1. 與星律同維度且距離星律方塊中心不超過 500 格的在線玩家。
2. AE CPU 保存的本次在線下單者，即使其位於其他維度或超過 500 格。

同一玩家同時命中兩條路徑時只發送一次。無法追溯下單者時仍向附近玩家廣播；附近無人且下單者離線時不保留離線訊息。

## 可點擊座標與安全

座標元件使用 `RUN_COMMAND` 呼叫山海命令，攜帶維度與方塊座標。該命令允許普通玩家執行，但服務端必須驗證目標維度已存在、目標區塊可取得，且目標位置仍是 `RecipeTypePatternBufferPartMachine`；驗證成功後才把玩家跨維度傳送到方塊上方安全位置。任一驗證失敗只回覆錯誤，不執行傳送。

命令不能接受任意非星律目標，也不能載入任意遠端區塊來完成驗證，以免成為無權限傳送或強制區塊載入接口。

## 錯誤處理

- EAEP 封包缺少新增尾部資料時保持向後相容，按空資料處理。
- 下單者作用域無 player id 時只記為未知，不阻止樣板發配。
- Pattern 解碼或配方狀態讀取失敗時保留基本卡死告警，單項診斷顯示未知，不能中止機器 tick。
- 主機控制器為空或已卸載時，原因顯示無可用主機；不嘗試跨區塊讀取。
- UI 警告同步不持久化；區塊載入後由樣板、主機與槽位原料重新計算，避免保存過期紅框。

## 測試與驗證

先以失敗測試鎖定以下行為，再寫生產碼：

- 精確主機類型相容、共享搜索集相容、已知類型不相容、未知資料不攔截。
- 手動選擇與唯一匹配自動上傳均經過二次確認，確認後不遞迴攔截。
- AE CPU player id 只在單次 provider push 作用域可見，異常時也會清理。
- 原料無變化達到閾值才告警；減少、增加、失活及清空會重設或清除狀態。
- 附近玩家與下單者合併後按 UUID 去重。
- `recipeStatus`、`workingStatus`、快取類型與輸出診斷正確聚合。
- 紅框只由警告狀態控制，仍保留既有緩存解碼與高亮繪製路徑。
- 傳送命令拒絕非星律、未載入或不存在的目標。

驗證順序為定向 JUnit 測試、相關 source contract 測試、`clean` 後完整 `build --no-daemon`。構建成功只證明編譯與自動測試通過；EAEP 畫面、聊天點擊與實際機器卡死仍需完整重啟遊戲後實機驗證。
