## 2. 原始快照層

### 2.1 資料結構

`RecipeOriginalSnapshotStore`（`common/recipe/RecipeOriginalSnapshotStore.java`）

```java
Map<String, LinkedHashMap<String, GTRecipe>> SNAPSHOTS;   // typeId → (stableKey → copy)
IdentityHashMap<GTRecipe, String> ANONYMOUS_KEYS;         // 無 id 配方的穩定鍵
long anonymousSequence;
```

- 全部方法 `synchronized`，回傳一律是 `recipe.copy()`（`copyOf`/`copiesOf`）。
- `capture()`：同 `(type,id)` 第二次捕獲直接忽略 → **首次為準**。
- 無 id 配方：`@anonymous:N` 遞增鍵，靠 `ANONYMOUS_KEYS`（identity）維持穩定。

### 2.2 捕獲時機

| 時機 | 方法 | 來源 |
|---|---|---|
| 規則載入後首次重建 | `ensureOriginals` → `captureManagerOriginals` | `RecipeManager` 的 `byType` 表（**完整**） |
| 上述拿不到 | `captureLookupOriginals` | `GTRecipeLookup.branch.getRecipes(true)`（**已被索引剪枝**） |
| `addRecipe` Mixin | `prepareLookupRecipe` → `captureOriginalRecipe` | 進來的第一個物件 |
| 編輯器找不到 id | `RecipeRebuildService.captureLive` | lookup 掃描 → RecipeManager 按 id 查 |

**關鍵設計**：先讀 `RecipeManager` 而非 lookup，因為 `GTRecipeLookup` 的添加演算法
在成分鍵衝突時會**丟棄後來的配方**（`recurseIngredientTreeAdd` 回傳 false 即不再插入），
從 lookup 反推原始配方會永久丟失衝突落敗者。此點在 `RecipeRebuildService:620-635` 有註解。

### 2.3 陷阱

- `captureLookupOriginals` 是降級路徑，一旦走到，快照就可能先天缺失配方；
  之後 `ensureOriginals` 因 `hasSnapshot==true` 不會再補。
- `clear(recipeTypeId)` 的匿名鍵清理邏輯寫在迴圈裡且依賴 `removed.containsKey(id)`，
  可讀性差、成本 O(n²)（詳見複查報告 P2-05）。

## 3. 規則層

### 3.1 內存規則

| 規則 | 容器 | 條目型別 | 語義 |
|---|---|---|---|
| strip | `Map<String, List<StripEntry>>` | `targetItem/isInput/isFluid/recipeId` | 從輸入或輸出移除匹配成分 |
| replace | `Map<String, List<ReplaceEntry>>` | `oldItem/newItem/oldIsFluid/newIsFluid/recipeId/count/circuitNumber` | 成分替換（含換成程式電路） |
| delete | `Map<String, List<DeleteEntry>>` | `recipeRegex` | 按 recipeId 正則整條刪除 |
| toggle | `Map<String,Boolean> PERSISTED_RECIPE_TOGGLES` | recipeId → false | 配方開關 |

值為 `CopyOnWriteArrayList`，外層 `LinkedHashMap`。註冊時若已存在同規則則**去重**（`sameStripRule`/`sameReplaceRule`）。

### 3.2 持久化路徑

全部經 `ShanhaiConfigPaths`（`config/gt_shanhai/recipe/…`）：

| 檔案 | 內容 |
|---|---|
| `strip_rules.json` | `{typeId: [{item,input,fluid,recipeId}]}` |
| `replace_rules.json` | `{typeId: [{old,new,oldFluid,newFluid,recipeId,count?,circuit?}]}` |
| `delete_rules.json` | `{typeId: ["regex", …]}` |
| `active_presets.json` | `["预设名", …]` |
| `presets/<name>.json` | 同 strip/replace/delete 的合併快照 |
| `recipe_overrides.json` | 編輯器覆寫（見 §6） |

配方開關**不在** config 目錄：`<gamedir>/kubejs/data/shanhai_recipe_load_config.json`，
同時被 `DShanhaiRecipeEnabledCondition`（datapack condition）與
`DShanhaiRecipeModifierAPI.PERSISTED_RECIPE_TOGGLES` 讀取——**兩套讀取同一檔案**，
因此手改該檔亦會影響資料包載入階段。

### 3.3 規則套用順序

`RecipeRebuildService.buildCanonical`（`:400-434`）：

```
original.copy()
  → applyStripByType(copy)        // 剝離
  → applyReplaceByType(copy)      // 替換
  → isDeletedByRuntimeRule(...)   // 刪除（回 null）
  → override.toGtRecipe(copy)     // 編輯器覆寫（若有）
  → 把 inputs/outputs/tickInputs/tickOutputs/conditions/duration/data 逐項覆蓋回 copy
```

順序固定，且每次都從快照副本開始 → **不會累積**。

### 3.4 已存在的實作細節

- `applyStrip`（API:414-464）遇到 Guava `ImmutableCollection` 會先複製成 `ArrayList`
  再 `put` 回去，避免 `UnsupportedOperationException`。
- `replaceInMap`（API:926-1005）就地改寫 `Content.content`，保留 `chance`/`maxChance`/
  `tierChanceBoost`；支援 `SizedIngredient`、`ItemStack`、原始 `Ingredient` 三種載體。
- 替換成電路時用 `IntCircuitBehaviour.stack(n)` 並 `setCount(count)`。

## 4. 重建層

### 4.1 整類重建 `rebuildType`

`common/recipe/RecipeRebuildService.java:53-125`

```
resolveType(typeId)                       // GTRegistries.RECIPE_TYPES
ensureOriginals(typeId, type)             // 快照（缺则抓）
overrides = overrideStore.entriesForType(typeId)
if (STARTUP || RELOAD) overrides = withoutSuperseded(...)   // 過期覆寫自動退休
rebuilt   = assemble(typeId, originals, overrides)
統計 dropped / replaced（按 id 去重與 shape 比對）
runPatternCacheInvalidationBatch(reason, () -> {
    SUPPRESS_LOOKUP_RECIPE_MODIFIERS = true
    lookup.removeAllRecipes()
    rebuilt.forEach(lookup::addRecipe)
    ShanhaiVanillaRecipeTable.replaceType(server, typeId, rebuilt)
    ShanhaiRecipeReverseIndex.invalidate()
    invalidateRecipeCaches(reason, Set.of(typeId))
    finally SUPPRESS = previous
})
if (reason != EDITOR_COMMIT) RecipeSyncPacket.syncToAll(Set.of(typeId))
```

`withoutSuperseded` 的判定（`:461-474`，有單元測試 `RecipeOverrideSupersedeTest`）：

| 條件 | 結果 |
|---|---|
| `created` 且資料包已有同 id | 退休（jar 已提供） |
| 資料包沒有來源配方 | 保留 |
| `baseFingerprint` 為空 | 保留（無法比對） |
| 指紋等於當前或 legacy 快照指紋 | 保留 |
| 其餘（jar 換版導致 base 改變） | **退休並從檔案刪除** |

### 4.2 增量刷新 `refreshLookupEntries`

`RecipeRebuildService:132-196`，供編輯器提交使用，避免整類 `removeAllRecipes()`：

1. 對每個受影響 id 求 `liveLookupRecipe`（套規則 + 套覆寫 + 排除禁用/被取代來源）。
2. `unlinkRecipes(Branch root, liveIds, removedIds)`：
   反射取 `Branch.nodes` / `Branch.specialNodes`（`Map<AbstractMapIngredient, Either<GTRecipe, Branch>>`），
   遞迴移除 `Either.left` 中 id 命中的配方，並清掉變空的子 Branch。
3. 成功 → 只 `addRecipe(live)`；失敗（欄位結構不符）→ **回退整類重建**。
4. 原版表走 `ShanhaiVanillaRecipeTable.replaceEntries(upserts, removals)`。

`BRANCH_NODES` / `BRANCH_SPECIAL_NODES` 以 `getDeclaredField` 靜態快取，取不到即視為不支援（回退）。

### 4.3 雙表寫回機制

`common/misc/RecipeManagerReflectionUtil` 反射定位 `RecipeManager` 的兩張私有 Map：

- `recipes`：`Map<RecipeType<?>, Map<ResourceLocation, Recipe<?>>>`
- `byName`：`Map<ResourceLocation, Recipe<?>>`

判定方式靠「key 型別」探測，並有 fallback（取前兩個 Map 欄位）。寫回時：

```java
ImmutableMap.copyOf(byType) / ImmutableMap.copyOf(byName)
ShanhaiRecipeTableHook.invalidateCaches(server)   // 清含 "cache" 的 Map 欄位 + Polymorph 玩家快取
```

**必須保持 ImmutableMap**：1.20.1 的 `RecipeManager` 在 `apply()` 直接以不可變集合替換，
若塞入可變 Map，某些第三方 mixin 會就地修改而污染資料包原表。

### 4.4 JEI 與客户端

- `JEIRecipeListMixin` 攔截 `RecipeManagerInternal.addRecipes`（最終收口），
  以 recipe id 去重（`JEIRecipeCache.filterUnseen`），並對有規則的 GT 配方建立修改副本。
- `BranchStripMixin` / `RecipeIteratorStripMixin` 是**兜底**：只處理非 canonical 物件，
  主要覆蓋機器迭代器與 JEI 早期收集路徑。
- `RecipeSyncPacket.refreshClient` 在客戶端隱藏舊 wrapper → 依本地 lookup 重建 → `addRecipes`，
  定向更新時用 `ShanhaiJeiRecipeViewSync.refreshCachedView`。

## 5. 編輯器資料層

### 5.1 DTO

`ShanhaiRecipeBase`（`common/recipe/editor/ShanhaiRecipeBase.java`）

| 欄位 | 來源 | 進 fingerprint |
|---|---|---|
| `recipeTypeId` / `recipeId` | 配方身分 | ✅ |
| `duration` | `recipe.duration` | ✅ |
| `eut` | `RecipeHelper.getInputEUt`，為 0 時取 `getOutputEUt` | ✅ |
| `inputs/outputs/tickInputs/tickOutputs` | `ShanhaiRecipeIoApply.tableJson` | ✅ |
| `conditions` | `RecipeCondition.CODEC` 逐條編碼 | ✅ |
| `blastTemp` / `recipeData` | `recipe.data` 的溫度等數值資訊 | ❌（刻意排除） |

`payloadJson()` 目前**只輸出前 5 類**，不含溫度欄位（見複查報告 P1-01）。

### 5.2 IO 编解码

`ShanhaiRecipeIoApply`：

- `tableJson(recipe, "inputs"|"outputs"|"tickInputs"|"tickOutputs")`
  → 只輸出 `item` / `fluid`（tick 額外 `eu`），用 `Content.codec(capability)` 編碼。
- `applyTable(recipe, which, json)`：先 `remove` 對應 capability，再 `parse` 重建。
- `euOf` / `applyEut`：`applyEut` 會同時寫 `data.euTier`
  （`GTUtil.getTierByVoltage(abs(eut))`）；若配方原本沒有 EU 成分則新建 `tickInputs.eu`。

### 5.3 溫度 / 資料資訊

`ShanhaiRecipeHeat`：

- `INT_KEYS`：`ebf_temp/temperature/SCTier/CATier/SEPMTier/nano_forge_tier/ev_min/ev_max/evt/FRheat/grindball`
- `LONG_KEYS`：`eu_to_start` / `eu`
- `sensitive(type, key, wide)` 用兩個極值 tag 跑一遍 `type.getDataInfos()`，
  輸出不同才視為「該類型真的有這個資料欄位」→ 避免對所有類型顯示無效欄位。
- `capture(CompoundTag)` / `write(CompoundTag, JsonObject)` 做 NBT ↔ JSON（數值型），
  `skip()` 排除 `batchSize/ocTier/ocLevel`。
- 線圈選擇：`ICoilType.ALL_COILS_TEMPERATURE_SORTED` → `"材料名 1800K"` 字串，
  反向解析用 `lastIndexOf('K')` 取數字。

### 5.4 覆寫儲存

`ShanhaiRecipeOverrideStore`（schema v1）：

```json
{ "schemaVersion": 1,
  "entries": [
    { "recipeId": "...", "sourceRecipeId": "...", "keepOriginal": true,
      "created": false, "recipeTypeId": "...", "baseFingerprint": "...",
      "updatedBy": "...", "updatedAt": "<ISO-8601>", "payload": { …ShanhaiRecipeBase.payloadJson… } }
  ] }
```

三種條目語義：

| 種類 | 判定 | 重建行為 |
|---|---|---|
| 就地覆寫 | `sourceRecipeId == recipeId`、`created=false` | 用 payload 改寫原配方 |
| 共存追加 | `sourceRecipeId != recipeId`、`keepOriginal=true` | 保留原配方，另加改寫版 |
| 取代追加 | `sourceRecipeId != recipeId`、`keepOriginal=false` | 移除原配方，加入改寫版 |
| 全新建立 | `created=true` | 不依賴快照，`materializeFresh` 生成 |

寫入流程：讀整份 → 過濾同名條目 → 追加 → 寫 `.tmp` → `ATOMIC_MOVE`（不支援則降級 `REPLACE_EXISTING`）。

### 5.5 提交校驗

`ShanhaiRecipeEditorOps.storeCommit`（`:131-183`）與 `ShanhaiRecipeEditorValidation`：

1. `valid(edit)`：type/id 非空、fingerprint 非空；
2. `validateBase`：`ResourceLocation` 合法、`duration ≥ 1`、四個表只允許
   `item`/`fluid`（tick 另允 `eu`）、每條 `Content` 必須能被對應 codec 解析、
   條件數 ≤ 256 且逐條可解析；
3. fingerprint 比對：`currentBase`（快照 + 覆寫 + 規則後的效果）與 `edit.baseFingerprint` 必須相等，
   否則回 `CONFLICT` 且**不寫檔**；
4. 共存/改名/新增的 id 衝突檢查（`liveIdTaken` 掃覆寫檔 + lookup + 快照）；
5. 寫入後回 `SUCCESS`，由呼叫方再 `refreshLookupEntries` + `syncRecipeToAll`。

`inheritLegacyDetails`：當 `baseFingerprint` 恰好等於 **legacy 指紋**
（不含 conditions/tickOutputs 的舊格式）時，把 payload 缺失的 `tickOutputs`
與 `conditions` 從原配方補回 → 兼容舊版存檔。

### 5.6 指紋

`ShanhaiRecipeFingerprint`：

- `PREFIX = "v3.sorted:json:"`
- 對 JSON 做 **object key 排序**（array 保序）後序列化；
- 超過 400 字元截斷為「前 220 + `~~` + 後 180」——指紋不是雜湊而是**可讀的簽名**，
  優點是能直接比對「哪一段變了」，代價是長度截斷後理論上可能碰撞。

## 6. GTCEu 1.4.4 底層行為（javap 實測）

### 6.1 `GTRecipe.copy()`

```java
public GTRecipe copy() {
    return new GTRecipe(recipeType, id,
        copyContents(inputs, null), copyContents(outputs, null),
        copyContents(tickInputs, null), copyContents(tickOutputs, null),
        new HashMap<>(inputChanceLogics), ...,
        new ArrayList<>(conditions), new ArrayList<>(ingredientActions),
        data, duration, isFuel);
}
```

- `copyContents` 逐個 `Content.copy(cap, null)`，而 `Content.copy` 會呼叫
  `RecipeCapability.copyContent()` → `copyInner()`，`FluidIngredient.copyInner` 呼叫 `.copy()`，
  因此成分**是深拷貝**。
- **`data` 是共享參照**（同一 `CompoundTag` 物件）。任何就地 `recipe.data.putInt(...)`
  都會污染所有副本與原表 → 修改 data 前必須先 `data = data.copy()`。
  現有 `ShanhaiRecipeIoApply.applyEut` 與 `ShanhaiRecipeBase.toGtRecipe` 都做了這一步。

### 6.2 `GTRecipe.equals/hashCode`

```java
public boolean equals(Object o) { return ((GTRecipe)o).id.equals(id); }
public int hashCode() { return id.hashCode(); }
```

→ 任何以 `GTRecipe` 為 key 的 Map 實際上都是「以 recipeId 為 key」。
這是 P0-01 的根因。

**已修（2026-10-20）**：`CANONICAL_LOOKUP_RECIPES` 改為
`Map<String typeId, Set<GTRecipe>>`，集合用
`Collections.newSetFromMap(new IdentityHashMap<>())` 做標識比較。
`rebuildType` 寫回後以本次副本 `replaceCanonicalLookupRecipes` 整體替換，
`refreshLookupEntries` 以 `unmarkCanonicalLookupRecipe` + `markCanonicalLookupRecipes`
維護增量，`isCanonicalLookupRecipe` 由配方自身的 `recipeType` 找對應集合。

### 6.3 `GTRecipeLookup.addRecipe`

```java
public boolean addRecipe(GTRecipe r) {
    if (r == null) return false;
    return recurseIngredientTreeAdd(r, fromRecipe(r), lookup, 0, 0);
}
```

- `fromRecipe` 把 recipe 的輸入/輸出成分轉成 `List<List<AbstractMapIngredient>>`（每個成分一層）。
- 樹是「成分路徑」，同一 recipe 會被插入多條路徑；衝突時後插入者可能**整體失敗**。
- `removeAllRecipes()` 僅清空 `Branch` 的兩個 Map，不動其他狀態。

### 6.4 `Branch`

```java
private Map<AbstractMapIngredient, Either<GTRecipe, Branch>> nodes;
private Map<AbstractMapIngredient, Either<GTRecipe, Branch>> specialNodes;
```

`getRecipes(boolean)` 回傳整棵子樹的 `Stream<GTRecipe>`（會產生重複）。
增量摘除必須同時處理 `nodes` 與 `specialNodes`，並在子 Branch 變空時移除節點
（`RecipeRebuildService.unlinkMap`）。

### 7.1 抑制旗標對照

| 旗標 | 型別 | 何時開啟 | 影響 |
|---|---|---|---|
| `SUPPRESS_LOOKUP_RECIPE_MODIFIERS` | `ThreadLocal<Boolean>` | 重建寫回、`removeDuplicate`、`replaceLookupRecipe` | `prepareLookupRecipe` 直接原樣返回 |
| `SUPPRESS_GET_RECIPES_STRIP` | `ThreadLocal<Boolean>` | 讀原始配方、掃描、`findLookupRecipeById` | `BranchStripMixin` 不加工 |
| `REAPPLYING_LOOKUP_RULES` | `ThreadLocal<Boolean>` | `reapplyPersistedLookupRules` | 防重入整包重建 |
| `LOADING_STRIP/REPLACE/DELETE` | `ThreadLocal<Boolean>` | 從檔案載入規則 | 避免邊讀邊寫檔與邊重建 |
| `LOADING_PRESET_BATCH` | `ThreadLocal<Boolean>` | 批次載入預設 | 同上 |

**ThreadLocal 是必要的**：載入流程可能在非伺服器執行緒（KubeJS 啟動腳本）發生。

## 8. 快取與 revision

### 8.1 三個層級

| 快取 | 位置 | 失效方式 |
|---|---|---|
| 機器查找結果 | `DShanhaiRuntimeRecipeCache` | key 含 `getRecipeTypeRevision(typeId)`；`clear()` 全清 |
| 樣板總成內部 | `RecipeTypePatternBufferPartMachine` 等 | 反射清 `cacheRecipe[]` / `recipeMultipleCacheMap` / slot cache |
| JEI 執行期 | `JEIRecipeCache` + `IJeiRuntime` 的 hide/add | `RecipeSyncPacket` 驅動 |

### 8.2 revision

```java
PATTERN_CACHE_REVISION : AtomicLong            // 全域
RECIPE_TYPE_REVISIONS  : Map<String, AtomicLong>  // 分類型
```

- `invalidateRecipeCaches(reason, typeIds)`：先對每個 type `incrementAndGet()`，
  再 `invalidatePatternCaches(reason)`（→ `PATTERN_CACHE_REVISION.incrementAndGet()`）。
- `invalidatePatternCaches` 若處於批次中就 `deferPatternCacheInvalidation`：
  只記 `dirty=true`，真正清快取與全域 +1 延到最外層批次結束（`endPatternCacheInvalidationBatch`）。
- **分類型 revision 不受批次抑制**，每次呼叫都會 +1 —— 因此同一批次內多次呼叫
  會讓快取鍵版本跳號，但不影響正確性（只影響命中率）。

### 8.3 owner 反射清理

`clearPatternCacheOwner(owner)` 依次：

1. `clearPatternCacheOwnerState`：`cacheRecipe`（boolean[]）→ 全 false；
   `recipeMultipleCacheMap` → `clear()`；`getInternalInventory()`（陣列）→ 逐槽
   `getCacheManager().clearAllCaches()` + `SlotCacheManagerAccessor` 重置電路快取。
2. `refreshAllByProduct()`
3. `gtShanhai$recipeCacheRevision` 欄位同步為當前 revision
4. `refreshPatternControllers`：對每個 controller 呼叫 `upDate()`、
   恢復 `MEPatternRecipeHandlePart` 快取、`RecipeLogic.markLastRecipeDirty()` +
   `updateTickSubscription()`（跳過 `PrimordialOmegaEngineModuleBase`）。

全部以 `findField/findMethod`（帶快取、沿父類向上）反射完成，任一失敗僅忽略。

## 10. 網路契約

### 10.1 通道

| 通道 | 位置 | 協議版本 | 方向 |
|---|---|---|---|
| `gt_shanhai:main` | `ShanhaiNetwork` | `6` | 逐包宣告 |
| `gt_shanhai:recipe_sync` | `RecipeSyncPacket.init()` | `3` | `PLAY_TO_CLIENT`（伺服器 → 客戶端） |

### 10.2 `RecipeSyncPacket` 格式（payload v3）

```
VarInt  version = 3
VarLong revision
Boolean fullRefresh
VarInt  typeIds.count  + UTF(512)×N     (上限 4096)
VarInt  updates.count  + [UTF id + GTRecipeSerializer.toNetwork]  (上限 64)
VarInt  removed.count  + UTF×N
```

v3 移除了客戶端從未讀取的 `recipeIds`（舊版全量刷新最多白寫 4096 個 id 字串）。

- 空 buffer → 回傳 `new RecipeSyncPacket()`（`fullRefresh=true`, rev=0）→ 舊版相容。
- 版本不符 → 同樣回空包（不拋錯），避免舊客戶端被踢。

### 10.3 編輯器封包

| 封包 | 方向 | 內容 |
|---|---|---|
| `RecipeEditorQueryPacket` | C→S | typeFilter / text / page / pageSize / sort / mode / ingredientKind |
| `RecipeEditorDetailPacket` | C→S | typeId / recipeId → 回 `RecipeEditorResultPacket(payload=base+blastTemp+recipeData)` |
| `RecipeEditorCommitPacket` | C→S | typeId / recipeId / baseFingerprint / payload(≤32767) |
| `RecipeEditorResultPacket` | S→C | status / message / revision / payload |
| `RecipeEditorExportPacket` | C→S | 匯出為 JS/KJS |
| `RecipeEditorDraftRequest/SyncPacket` | 雙向 | 草稿跨 session 保存 |
| `RecipeEditorMachinePacket` | C→S | 查機器槽位容量 |
| `RecipeEditorEncodePacket` | C→S | 直接編碼樣板 |

狀態列舉（兩處重複，值一致）：`SUCCESS / CONFLICT / VALIDATION_ERROR / REBUILD_FAILED / PERMISSION_DENIED`。

權限：所有 C→S 編輯器封包入口皆檢查 `sender.hasPermissions(2)`（8 處），
失敗回 `PERMISSION_DENIED`，不執行任何寫入。

## 12. 已知陷阱清單（實作向）

1. **`GTRecipe.data` 是共享的**，改它之前一定 `copy()`。
2. **`GTRecipe.equals` 只比 id**，不可作為「版本/實例」判別；也不可作為 WeakHashMap 的語義鍵。
3. **`lookup` 會剪枝**：成分鍵衝突時後插入者被丟棄，不能當作原始配方全集。
4. **`RecipeManager` 的 map 必須是 ImmutableMap**，寫回時要重新包 `ImmutableMap.copyOf`。
5. **`Branch` 有兩張 Map**（`nodes` / `specialNodes`），漏一張就會殘留幽靈配方。
6. **`SUPPRESS_*` 是 ThreadLocal**，跨執行緒呼叫（KubeJS / 網路執行緒）時不會繼承。
7. **`setRecipeEnabled` 的 key 是 `typeId + "|" + fullId`**，取用時靠 `substring(indexOf('|')+1)`，
   若 typeId 或 id 含 `|` 會解析錯（目前 ID 規範下不會）。
8. ~~**`payloadJson()` 不含溫度欄位**~~（已修：`payloadJson()` 已納入 `blastTemp`/`recipeData`；
   基準指紋改由 `fingerprintJson()` 產生，刻意排除溫度，避免既有覆寫檔失效）。
9. ~~**`refreshLookupEntries` 的統計欄位語義**與 `RebuildReport` 定義不一致~~（已修：`captured`/`replaced`
   改用實際輸入與寫回數量）。
10. ~~**`RecipeSyncPacket` 自建通道未限制方向**~~（已修：`Optional.of(NetworkDirection.PLAY_TO_CLIENT)`）。
11. **`runRuleBatch` 是執行緒本地的批次深度**：批次內的規則註冊只記錄待重建類型，
    由批次收尾統一重建；跨執行緒呼叫不會繼承，需各自開批次。
12. **`applyContentTransform` 會寫覆寫檔**：`replaceBatch`/`replaceAllRawOres`/`replacePatternRecipes`
    的結果持久化在 `recipe_overrides.json`，不是一次性記憶體改動。
